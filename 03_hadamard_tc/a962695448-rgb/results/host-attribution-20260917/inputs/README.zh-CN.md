# 普通调用计时的交叉诊断

当前生产计算源码保持原版。此前两版成对 Hadamard 的 REJECT 判定保留；本次仅做归因诊断，不据此采用 kernel。

## 已确认的离线现象

最严重的 FP16 fused / rows16387 / N2 allocating 慢例：两侧单独中位数相除为0.809675，但9组成对观察中5组候选更快，组内比值中位数为1.007713。前6组的两侧时间均有大幅起伏，最后3组接近8微秒。不能据独立中位数的比值推断稳定退化，也不能据配对比值把旧失败改写为成功。

静态汇编中，quantized<true>、quantized_out<true> 入口分别都是380和396条记录指令，两版 opcode 序列和直接调用目标名称相同；被调用的 dispatch<true,true> 从97变为277条，并在 packed 路径出现额外 size 查询。计数含错误/冷分支，不是动态成本，callee 实现及重定位仍不同，不能直接归因。

## 冻结的新诊断

- 三个新进程，循环交换模块加载顺序。control_a/control_b 用同一源码路径、相同参数、等长不同模块名编译，测试同源不同模块带来的差异。
- 四种有依据的配置；每种同时测三个共用输出池、轮换独立输出池与分配式调用。18组完整覆盖六种测量顺序×三种缓冲区轮换，每块5000次。
- 保存墙钟、进程/当前线程CPU时间、时间线、调度/缺页/GC计数及可用CPU频率。保留所有样本，不筛选或自动重复直到通过。
- 对照/候选和全部输出池先核对独立CPU参考，结束再核对输入及结果。以同源A/A、跨进程方向和原始波动描述诊断；不生成优化采纳结论。

`python tools/analyze.py /path/to/run --output diagnosis.json` 复算完整设计。三个合成测试已覆盖完整矩阵、丢失记录/错误输出池拒绝，以及独立中位数与配对方向冲突。GPU尚未运行。

在准备好的RTX4090环境：`OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 python run.py`。结果回收、哈希校验后关机。
